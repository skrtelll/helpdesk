# Отчёт по frontend-спринтам: интеграция с API и авторизация

Работа выполнена по контракту `HelpDesk_System_API_Documentation.md` (v1.2, 14.10.2026) и по двум таблицам задач. Backend из `backend.zip` использовался для сверки (см. «Расхождения»).

## Что сделано

### Таблица 1: интеграция и состояния

| Задача | Результат |
|---|---|
| Интеграция с API (Fetch), замена демо-данных | Единый HTTP-клиент `src/shared/api/http.ts` на `fetch`. Подставляет `Authorization: Bearer`, строит query-параметры, превращает ошибки в `ApiError` (код, сообщение, `fieldErrors` по п. 11). Данные заявок, очереди, категорий и профиля читаются и пишутся через API; заглушек нет. Запросы идут на `/api/v1/*` своего origin, Next.js проксирует их на backend (`next.config.mjs`), CORS не нужен. |
| Состояния Loading / error / empty для всех экранов | Списки, карточка заявки, очередь: индикатор загрузки, ошибка с кнопкой «Повторить», пустое состояние. Ответ 403 показывает экран «Нет доступа» (п. 9.1). Формы Login, Register, CreateTicket: блокировка кнопки на время запроса и ошибка над формой, ошибки полей (422) подсвечиваются под полями. Каркас `Protected`: загрузка пользователя, ошибка связи, нет доступа по роли. |

### Таблица 2: авторизация, очередь, роли

| Задача | Результат |
|---|---|
| Auth-экраны: Login, Register, токены, refresh, logout | Формы с валидацией (email, пароль от 8 символов, имя до 100). После входа access и refresh token хранятся в `localStorage`. При ответе 401 клиент один раз вызывает `POST /auth/refresh` (токен ротируется), повторяет запрос; параллельные запросы делят один refresh. Если refresh отклонён, токены очищаются и пользователь попадает на `/login`. «Выйти» вызывает `POST /auth/logout` и очищает токены даже при ошибке сети. Вошедшего пользователя со страницы входа перенаправляет к его разделу. |
| Очередь поддержки: фильтры, сортировка, кнопка take | `/support/queue` на `GET /support/queue`: фильтры по категории, приоритету и «только без исполнителя» (параметры из п. 7.6); серверная сортировка (по умолчанию приоритет по убыванию, затем старые; также «Сначала старые», «Сначала новые», «Недавно обновлённые»); серверная пагинация. Кнопка «Взять» есть в очереди и в карточке заявки: перед вызовом читается актуальная `version`, затем `POST /tickets/{id}/take` с `{ version }`. При `409 ALREADY_ASSIGNED` и других конфликтах показывается сообщение, список обновляется. |
| Роли: скрытие недоступных действий | Роль берётся из `GET /users/me`. Пункт меню «Очередь», страница очереди и кнопка «Взять» доступны только SUPPORT и ADMIN; для USER они скрыты, прямой переход на очередь показывает «Нет доступа». Создание заявки доступно всем ролям (матрица п. 3.4). Это только UX: права проверяет backend (BR-002). |

## Что принято по контракту

- Заявка в списках (`GET /tickets`, `GET /support/queue`) не содержит `description`, `author` и `version`; полная заявка (`GET /tickets/{id}`, `POST /tickets`) их содержит. Типы `TicketSummary` и `Ticket` разделены. Категория и исполнитель приходят объектами (`category: { code, name }`, `assignee: { id, displayName } | null`).
- В списке заявок показываются статус, категория, приоритет, исполнитель и дата создания (п. 9.3); категории в фильтре очереди — из `GET /categories` (только `code`, `name`, `description`).
- Для `logout` тело запроса в документации не описано: отправляется `{ refreshToken }`, как для `refresh`.

## Ограничения

- В документации (п. 9.5) в очереди упомянуто «количество критических заявок», но в таблицах задач такого пункта нет, поэтому оно не сделано. Значение доступно в `GET /statistics/overview` (`criticalOpen`).
- Комментарии, история, отмена и закрытие заявки, «Мои заявки», рабочее место сотрудника и админ-панель в этих спринтах не реализованы: их нет в таблицах задач.
- Токены хранятся в `localStorage`: для учебного проекта достаточно, для продакшена лучше httpOnly cookie.

## Изменённые и новые файлы

- `next.config.mjs`, , временный `X-User-Id`.
- `src/shared/api/`: HTTP-клиент, refresh токенов, хранение токенов, тип страницы.
- `src/shared/ui/States.tsx`: состояния Loading, Error, Empty, «Нет доступа» (403 показывается вместо ошибки).
- `src/entities/`: `ticket` (типы по контракту, API списков, очереди, карточки и создания), `category`, `user` (сессия, роль, `homePath`).
- `src/features/auth/`: формы входа и регистрации, `Protected` (шапка, меню по роли, выход, ограничение по роли), logout.
- `src/features/ticket-take/`: кнопка «Взять» и правило, когда её показывать.
- `src/pages/`: страницы подключены к API и обёрнуты в `Protected`; новая `support-queue`; карточка заявки берёт `id` из адреса.
- `src/app/providers/AppProviders.tsx`: `SessionProvider`. `app/support/queue/page.tsx`, `app/tickets/[id]/page.tsx`.
